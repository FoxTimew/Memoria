# Session 4d — NAT de bureau et délais par compte

Sur `codex/session-4-strong-auth`, après validation manuelle de 4c. La livraison s'arrête ici pour relecture ; 4e n'est pas commencée. Pas de PR intermédiaire : le développeur crée et fusionne la PR unique après 4f. La description `.local/session-4d-pr.md` complète celles de 4a–4c.

## Ce qui change

Cinquante personnes peuvent se connecter derrière la même IP de bureau. Un compte ciblé par plusieurs IP rencontre un délai progressif avant vérification du mot de passe, sans verrouillage permanent. Une tentative déjà admise conserve son échéance même si de nouveaux échecs arrivent. Les calculs et les requêtes en attente sont bornés dans PostgreSQL, donc partagés entre instances API.

Les règles retenues dans l'ADR 015 sont actives : 150 connexions/minute/IP, 100 inscriptions/dix minutes/IP, 150 renvois de vérification/cinq minutes/IP, 100 demandes et validations de reset/dix minutes/IP, 300 appels par route de facteur/minute/IP, 600/minute/IP pour les autres routes d'authentification. Les routes métier gardent leurs autorisations et ne font pas partie de ce quota d'authentification.

Après cinq échecs sur quinze minutes : 1, 2, 4, 8, 16 puis 30 secondes maximum par tentative. Un succès complet remet le compteur à zéro, sans qu'un ancien échec encore en vol puisse le rétablir. La passkey reste accessible sans attendre la file de mots de passe. Les codes de récupération ont désormais un défi de cinq essais/cinq minutes lié au compte et au parcours ; sa création est aussi soumise au délai du compte.

Les emails sont limités par destinataire et type à 3/quinze minutes et 10/jour, configurables. Le renvoi de vérification utilise désormais le worker comme le reset : réponse générique, puis livraison asynchrone. Le worker purge les compteurs inactifs après vingt-quatre heures, configurable, et les défis/réservations expirés. Le guide opérateur impose une vérification d'identité en personne ou visio, jamais un simple message/email, avec confirmation indépendante si possible et motif sans donnée personnelle.

## Ce qui pourrait casser

- Déployer l'API sans la migration 0014 empêche l'authentification. Déployer API et worker avec les mêmes valeurs de configuration/secret. Le worker doit tourner pour les emails de vérification comme de récupération.
- Une file pleine peut rejeter **une nouvelle** tentative avec 429 (huit réservations par compte/famille, 128 globales). La garantie d'attente concerne une tentative **déjà admise**. La récupération a sa propre famille ; la passkey n'attend pas la file des mots de passe. Une saturation globale reste possible.
- Le plafond d'emails peut être consommé par des demandes hostiles. Un lien valide déjà reçu reste utilisable ; le reset/renvoi ne dit pas si un compte existe ni si le quota a été épuisé. Les notifications de sécurité répétées peuvent être supprimées ; l'audit n'est pas supprimé.
- Deux vérifications successives de récupération (création de défi puis consommation) peuvent chacune attendre trente secondes. L'interface prévient qu'une minute peut être nécessaire. Recharger perd le défi en mémoire ; le nouveau défi reste ralenti.
- Une panne API peut laisser une réservation pendant deux minutes. Arrêter le worker arrête la purge des compteurs, mais pas l'expiration logique des fenêtres lors des appels API.
- Les erreurs 4xx de routes protégées sont comptées conservativement, y compris certains refus de politique. Aucun échec n'interdit à lui seul le bon mot de passe après le délai.

La politique « Poste partagé » et l'interdiction du cache restent en 4e. La revue adverse 4f, la comparaison collaborative alternée avec main sur secteur (10 % maximum) et la qualification dédiée restent obligatoires. Aucun benchmark de performance n'est lancé dans cette livraison. La purge générale des journaux de sécurité reste une étape ultérieure de rétention.

## Guide manuel pas à pas

1. Mettre la branche à jour, démarrer PostgreSQL/Caddy/Mailpit, lancer `pnpm db:migrate`, puis `pnpm build` et démarrer les services comme dans le guide d'hébergement. Les services locaux de cette livraison sont déjà redémarrés. Ouvrir `https://localhost`, Mailpit `http://localhost:8025`, et une fenêtre privée. Employer deux comptes de test différents ; garder un moyen fort et des codes de secours disponibles.
2. Dans la première fenêtre déconnectée, saisir cinq fois un mauvais mot de passe pour le compte A. À la sixième tentative, saisir le bon. Observer « Vérification en cours », le bouton temporairement désactivé et environ une seconde d'attente, puis la connexion ou l'écran de second facteur si A en possède un.
3. Pour voir les paliers suivants, refaire ce parcours sur un autre compte de test avec des erreurs successives : après cinq erreurs, 1, 2, 4, 8, 16 puis 30 s. Ne pas attendre une réponse instantanée et ne pas multiplier les clics. Pendant l'attente de A, connecter B dans la fenêtre privée : son propre compteur est indépendant. Une fois A authentifié complètement, sa tentative suivante ne porte plus le délai d'échecs précédent.
4. Si A a une passkey, vérifier qu'une connexion par passkey reste possible. Si le mot de passe vient de réussir mais que le second facteur n'est pas encore vérifié, ne pas considérer le compteur comme réinitialisé ; le test serveur prouve cette différence.
5. Demander un lien de récupération pour une adresse de test connue puis inconnue : le même message est affiché. Répéter cinq fois pour l'adresse connue depuis une fenêtre de quota neuve : au plus trois demandes sont acceptées pour envoi en quinze minutes. Vérifier les messages dans Mailpit ; ouvrir un lien déjà reçu fonctionne même après épuisement du quota. Le test automatise la borne quotidienne sans attendre un jour. Ne pas modifier les compteurs d'utilisateurs pour accélérer l'essai.
6. Refaire une récupération avec un code de secours sur un compte de test : mot de passe + code, session de rétablissement seulement, nouvel enrôlement, fin, puis nouvelle preuve forte. Pour la commande opérateur, suivre d'abord la vérification en personne/visio et la confirmation indépendante du guide. Ne jamais accepter un email seul comme preuve.
7. Pour les trois scénarios bloquants, lancer `pnpm test:auth:limits`. Le résumé doit être **12 réussis, zéro échec**. Lire les lignes `Observed admission` et `Real admitted victim wait` : 50 succès derrière une IP, huit actifs maximum, tentative légitime à un peu plus de trente secondes malgré l'attaque. La suite crée/nettoie son propre schéma ; elle ne modifie pas vos comptes.
8. Pour reproduire les parcours visibles : `pnpm test:auth:limits:browser`, puis `pnpm test:auth:recovery:browser`. Ils utilisent Caddy HTTPS, la CA approuvée, le worker et Mailpit, créent des comptes temporaires puis les suppriment. La capture de l'attente est dans `.local/session-4d-wait.png`.
