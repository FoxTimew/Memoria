# Session 5b — invitations, membres et arrivée avec connexion forte

Livraison du 25 octobre 2026 sur `codex/session-5-guests-sharing`, après 5a validée. **À relire avant 5c.** Pas de PR créée ; description intermédiaire dans `.local/session-5b-pr.md` pour la PR finale de session 5.

## Ce qui fonctionne

Owner/admin peuvent inviter, copier le lien, renvoyer ou annuler, consulter les listes paginées et gérer les membres selon leur rôle. Admin gère member/guest et le cache ; seul owner gère admin/owner et l'obligation de connexion forte. Le dernier owner ne peut pas être retiré. Une promotion guest efface ses anciens partages ; une rétrogradation impose un nouveau choix. Retrait puis réinvitation ne restaurent pas les anciennes permissions.

Toute mutation d'accès exige une preuve forte récente, même dans un studio où elle est facultative. Si elle manque, le formulaire d'invitation est conservé pendant la configuration/vérification, puis proposé à nouveau, sans envoi automatique. Le même écran sert à owner et admin. Les actions de gestion restent à confirmer au retour.

L'acceptation vérifie le destinataire, son email, les droits actuels de l'émetteur, l'expiration, les racines et les plafonds. Membership, acteur, sujet, grants, audit et notification sont atomiques avec Better Auth. Un nouveau membre d'un studio imposant MFA n'a aucune grâce ; l'enrôlement seul ne lui ouvre pas le contenu. Le parcours le guide vers la vérification puis vers le studio. Les invités terminent leur adhésion/MFA mais leur éditeur navigateur reste fermé jusqu'à 5c.

### Routes montées et quotas R12

Préfixe `W = /api/internal/workspaces/:workspaceId`. Toutes passent par le guard global, sans `@Public`, puis par les contrôles du service. Elles refusent un anonyme et une session restreinte dans le test R12. Le test préremplit **chaque** compteur IP canonique et exige un 429 sur la route réelle. `Retry-After`, proxy non fiable, variantes et quota de compte sont testés séparément.

| Méthode / route                                                                                  | Famille |
| ------------------------------------------------------------------------------------------------ | ------- |
| GET `W/invitations` ; GET `/api/internal/invitations` ; POST `/api/internal/invitations/resolve` | read    |
| POST `W/invitations` ; POST `W/invitations/:id/resend`                                           | send    |
| POST `W/invitations/:id/cancel`                                                                  | mutate  |
| POST `/api/internal/invitations/accept` ; POST `/api/internal/invitations/reject`                | respond |
| GET `W/arrival` ; GET `W/members` ; GET `W/security`                                             | read    |
| PUT `W/members/:memberId/role` ; DELETE `W/members/:memberId` ; PUT `W/security`                 | mutate  |

`read` : 600/min/IP/gabarit, 120/min/compte ; `send` : 100/10 min/IP/gabarit, 50/10 min/acteur/workspace et 200/jour/workspace ; `respond` : 150/5 min/IP/gabarit, 30/5 min/compte ; `mutate` : 60/min/IP/gabarit, 30/min/acteur/workspace. Création/renvoi partagent le budget de compte ; acceptation/refus aussi. Email : 3/15 min et 10/jour/destinataire/type, sans reconsommation lors des retries. Voir [ADR 018](../adr/018-invitations-et-arrivee-workspace.md).

## Ce qui pourrait casser

- Migration 0018 nécessaire avant le nouveau serveur/worker. La FK des intentions de partage empêche la suppression définitive d'une page encore référencée ; la future purge nettoiera ces intentions. L'archivage reste autorisé et bloque l'acceptation.
- SMTP exige le worker et le même secret que l'API. L'état affiché est une photographie : actualiser pour suivre l'envoi. Une invitation reste valable si SMTP échoue ; utiliser son lien copiable. Un ancien lien après renvoi est toujours inutilisable.
- Tous les verrous de pages du workspace sont encore pris pour les mutations d'accès. **5d doit mesurer partage, rôle, retrait à 1 000 pages pendant des écritures sur plusieurs documents**, durée de mutation et attente des éditeurs. Les bases de session 6 devront revoir ce verrou global avant de dépasser la borne.
- L'interface guest et la gestion des grants après invitation restent en 5c, avec purge de cache et preview des déplacements. `409 SHARING_PREVIEW_REQUIRED` reste provisoire ; **aucun merge de la session avant sa levée en 5c**.
- Une réinvitation conserve les anciens acteurs historiques pour les contributions, mais crée une nouvelle membership/sujet. Elle ne réactive pas les anciennes clés API ou permissions.
- Les risques et prérequis 4f, notamment RGPD R13, crash R09 et qualification 4 vCPU/8 Gio R11, ne changent pas. Aucune nouvelle acceptation de risque implicite.

## Guide manuel — environ quinze minutes

1. Installer la version de cette branche : `pnpm db:migrate`, reconstruire/redémarrer API, worker, front et collab. Caddy/Mailpit doivent tourner ; ouvrir `https://localhost`. Aucun reset de contenu. Pour rejouer l'automatisation : `pnpm test:invitations:browser`.
2. Avec un compte **sans facteur**, créer un studio et ouvrir ses pages puis « Membres et invitations ». Préparer une invitation member vers une deuxième adresse accessible dans Mailpit. Cliquer « Envoyer » : aucune invitation ne doit partir ; un message propose de configurer/vérifier son identité.
3. Suivre le lien. Configurer au choix le QR TOTP sur Android ou une passkey Windows Hello/YubiKey. Conserver les codes de secours. L'enrôlement seul ne suffit pas : vérifier ensuite son identité (pour TOTP, attendre le prochain code si celui d'enrôlement a déjà été utilisé). Cliquer « Reprendre mon action ». Le formulaire est rempli, aucune invitation envoyée automatiquement. Cliquer à nouveau « Envoyer ».
4. Vérifier l'email dans `http://localhost:8025` et le lien copiable dans la page. Actualiser pour voir « Email envoyé ». Ouvrir le lien dans une fenêtre privée **sans compte connecté** : aucun nom de studio ni de page ne doit apparaître.
5. Créer le second compte avec l'adresse exacte, vérifier l'email Mailpit puis se connecter. Revenir au lien si nécessaire, ou « Mes invitations ». Le studio apparaît ; accepter explicitement. Un autre compte vérifié doit seulement recevoir le message générique, jamais l'adresse attendue.
6. Tester un autre lien en attente : « Renvoyer » côté gestionnaire, puis ouvrir l'ancien lien côté destinataire : refus. Le nouveau marche. « Annuler » le rend également inutilisable. Ne pas multiplier plus de trois envois vers la même adresse en quinze minutes : l'état indique alors la limite et propose le lien copiable.
7. Avec l'owner, activer l'obligation forte du studio dans sa politique. Inviter un **nouveau** compte sans facteur, member ou admin. Après acceptation, il doit être guidé immédiatement vers QR/passkey, même avec grâce de sept jours. Il n'obtient « Ouvrir le studio » qu'après la preuve forte. Répéter avec un guest : adhésion/MFA disponibles, écran d'attente de 5c au lieu de l'éditeur.
8. Inviter un admin. Sans facteur, sa tentative d'inviter un member/guest doit suivre le même parcours guidé. Après vérification, il peut inviter ces rôles, changer le cache, retirer un member/guest ; il ne peut ni attribuer admin/owner, ni gérer leur rôle, ni changer l'obligation MFA. Ces tentatives forgées sont aussi couvertes par le test serveur.
9. Créer deux pages distinctes, inviter un guest sur une racine read ou edit. Dans la gestion des membres, le promouvoir member puis le rétrograder guest : nouveau choix obligatoire des racines. Retirer un membre qui a une page ouverte dans l'autre navigateur : connexion collaborative fermée, accès refusé. La nouvelle invitation ne restaure que les racines choisies ; le test serveur vérifie l'ancienne page encore refusée.
10. Relire les résultats et les absences ci-dessus, puis valider 5b. Les essais navigateur read/edit, modification des partages, cache et déplacements avec aperçu seront le guide 5c ; les mesures et attaques consolidées, celui de 5d.
