## Résultat à retenir

Le vrai front conserve les 90 saisies de l'auteur après une rafale CPU de **3 721 ms**, mais le journal n'avance que de 78 révisions et le second navigateur n'affiche que 78 saisies. Les **12 dernières restent non confirmées**. L'auteur ferme sa socket en code 1000, en ouvre une autre 1 606 ms plus tard, puis reçoit un code 1008 après 69 ms. Son écran reste « Édition arrêtée », plus de **30 secondes après la fin de toute la charge**. L'autre navigateur reste connecté. Le test échoue réellement ; ce n'est pas un succès attendu ni un test désactivé.

**Aucun `CONTROL_UNAVAILABLE` n'a été observé.** Le défaut 1008 est distinct des fermetures 7a encore inexpliquées. Les caractères restent visibles dans le document de l'auteur, avec le parcours d'export proposé ; leur survie à la fermeture du navigateur dans cet état n'a pas été testée. Ne pas présenter cette conservation locale comme un enregistrement sur le serveur ni comme la preuve complète « aucune perte ».

## Diagnostic et limites

Le dernier renouvellement avant la rafale se termine à 22:07:17,621 ; le suivant à 22:07:21,789 : **4 168 ms entre confirmations**. Le [contrôle de leadership](../../apps/collab/src/service/leadership.ts) refuse un âge local supérieur à 2 500 ms ; le bail SQL est de 3 000 ms. La rafale franchit les deux fenêtres. Toutes les requêtes instrumentées finissent pourtant avec succès : aucune erreur timeout SQL capturée. Le `query_timeout` JavaScript de 1 500 ms n'a donc pas garanti un retour dans ce délai lorsque la boucle était bloquée.

Le [client](../../apps/web/src/lib/collaboration-client.ts) arrête durablement l'édition sur code 1008 ou refus d'authentification. Le [serveur](../../apps/collab/src/service/server.ts) et [public-error](../../apps/collab/src/service/public-error.ts) regroupent plusieurs erreurs techniques derrière des codes publics génériques. C'est compatible avec le blocage observé, **mais le chemin exact reste à confirmer** : le filtre de traces a enregistré `other` pour le motif du 1008, et les sorties serveur brutes n'ont pas été conservées. La chronologie suggère un contrôle de leadership devenu périmé ; elle ne prouve pas quel refus a empêché la deuxième synchronisation. Aucune révocation de compte ou modification de droits n'a été introduite dans ce test.

Indépendamment de ce nouveau cas, `fail()` marque actuellement le service indisponible sans réarmement ; ce chemin global `CONTROL_UNAVAILABLE` demeure sans reproduction sous CPU et sans preuve de reprise. Il doit rester dans la matrice.
